# Review: T16 read — the turn is a per-player clock

*Change: documentation only. `docs/mechanics/determinism.md` gains "The turn, read", `docs/decisions.md` gains D232, the tree's
T16 row now says what the turn is, and `docs/next-step.md` prices the build. **No simulation code changed** - `git diff --stat`
under `crates/` is empty.*

## Performance

**Zero: 0 lines changed under `crates/`, 0 files added to the crate tree.** The gate's numbers therefore stand unchanged in
kind — 193 binaries, 880 passed, 0 failed, 20 ignored — and the cost of the step is reading time, not frames.

The step's *product* is a number, though, and it is the one that decides the next slice: **one rotating index plus 9
per-player clocks** (`+0x104..+0x124`, verified by the reset at `baseworld.cpp:0x24b` clearing `+0x100` and exactly nine
words), which the DE port consumes at **two call sites** (`world/schedule.rs:274` and `:323`).

## Stability

- **Three sources agree, and none of them is a summary of another.** Our binary's `BaseWorld::update` accumulates per player
  and zeroes the turn player's word; its reset function names the array (nine words, no more, no fewer); its getter reads one
  word by player index; the DE port implements the same two lines and shows the *consumer*; and the save's world header carries
  both fields, so the shape survives a save round-trip. A reading that only had the port would have been "DE's turn"; this one
  has 5.7's own fields and offsets.
- **The consequence that stops the build is stated as a consequence, not as a shrug.** The turn needs a per-player clock and a
  two-tier unit AI. Our engine has neither, and the *second* is not an implementation detail: "the full update on the owner's
  turn, a cheap check otherwise" is a reaction-cadence decision, and picking a cadence is inventing a rule. D232 says that in
  those words, so the next session cannot mistake the omission for an oversight.
- **The one piece that needs no ruling is named**: `pturn` and the nine clocks are **save fields**, so `P1` owes them either
  way. That gives a later slice a landing point with a test (a save's header round-trips; the rotation advances, wraps, and
  zeroes the current player's clock) without touching behaviour.
- **What would have made this wrong, checked before writing it**: that `pturn` is a *scheduling* order (it is not - it gates a
  clock), that the per-player array might be something else (the reset zeroes exactly nine words right after `pturn`, and the
  getter indexes it by player), and that the port's reading might be DE-only (5.7's update does the same zero-and-advance).

Known and accepted:

- **No mechanism was written**, deliberately: a turn with no consumer is inert code, and this tree's rule is that a mechanism
  with no reachable trigger is not written (D223's lesson, applied twice since).
- **The AI split is not scheduled.** If it is wanted, it is a design question for the owner - how the computer player's
  reactions should be paced - and `docs/next-step.md` says so rather than queueing it behind a debt number.
