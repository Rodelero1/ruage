# Names: 1,390 readable identifiers, derived from the game's own strings (2026-11-02)

Scope: `tools/names.py` (new), `tools/test_names.py` (new, 13 tests), `config/names.toml` (new, 1,390 entries).

The owner's ask: the unit names in the generated tables are cryptic (`KNGHT`, `ISPKM`, `HEROC`) and should read like
`villager`, `elite_cataphract`. Every populated unit, corpses included.

## Why the dat's codes could not be translated

They are not names, and they are shifted: 283 says `PALDN` and is the **cavalier**; 569 says `HEROC` and is the
**paladin**; 7 says `XBOWM` and is the **skirmisher**; 74 says `SPRMN` and is the **militia**. Any code-to-name table
built on them inherits the shift.

The trustworthy source is the string the dat itself points at. Every unit record carries `name_str_id`, and the
install's `key-value-strings-utf8.txt` turns that id into "Elite Cataphract". Verified before writing anything: 38 ->
5068 "Knight", 283 -> 5070 "Cavalier", 7 -> 5088 "Skirmisher", 359 -> 5409 "Halberdier", 83 -> 5121 "Villager".

## What the derivation covers

| | count |
|---|---|
| unit records in the dat (union over the 32 civilisations) | **1,388** (+ id 0 = 1,389, matching the pack) |
| populated records (`hp > 0`) | **1,132** |
| populated records the game gives a display name | **846** |
| populated records carrying the sentinel `name_str_id = 5000` | **285** |
| populated records left unnamed | **0** |
| names written (units + corpses) | **1,390** |
| display-name collisions resolved by suffix | **413** |

The 285 are the editor's props, scenery and scenario-only objects — `TERRC`, `WNDR`, `INDESTRUCT`, `OLD_EXPLORER`.
The game has no word for them either, so they fall back to their **code**, slugged: `terrc`, `wndr`. That is ugly on
purpose: a code-shaped name is honest about the fact that nobody named it, and it is stable.

Corpses are named after what leaves them (`dead_unit_id`), which is why `449` is `scout_cavalry_corpse` and not
`scout_d`, and why a boar and a javelina sharing one body get the **base animal's** name (`wild_boar_corpse`).

## Performance

**1.05 s** for the whole derivation (parse the dat, load 12,563 strings, name 1,388 records, render 1,399 lines), of
which the dat parse dominates. It is an authoring step, run by hand when names change; nothing reads it per tick. The
test suite is **13 tests in 1.03 s**.

`config/names.toml` is 26 KB — 1/20th of `units.toml` — because it carries words, not statistics.

## Stability

- **Names are unique and snake_case**, and both are asserted against the project's own table, because a name becomes an
  identifier the moment anything refers to a unit by it.
- **The shifted codes are pinned by four assertions** (283 cavalier, 569 paladin, 7 skirmisher, 359 halberdier). If a
  future derivation ever regresses to the dat's codes, those fail with the code in the message.
- **Collisions are reported, not hidden**: the tool prints each one (`unit 20: 'Barracks' collides with unit 12, named
  'barracks_2'`) so a human sees that the age variants of a building share a display name.
- **A corpse never takes its `_D` code as a name**, and two animals sharing a body resolve to the base animal, not to
  whichever happens to be iterated last.
- **One name is an id the pack does not carry**: 768, the corpse that `SPEC.md` already records (640 records point at it,
  and no civ has it). Harmless — it can never be looked up — and noted here rather than quietly filtered.

### What I got wrong on the way

- **The first collision resolution was a bug that produced a garbage message** (`by_id[used and record.id]`), found by
  running it rather than by reading it.
- **The corpse pass ran after the code fallback**, so `449` came out as `scout_d` — exactly what the owner asked not to
  have. Fixed by naming corpses before the fallback.
- **My first "populated" count (1,132) came from the pack while a dat probe through civ 1 said 962.** The difference is
  real: civ 1's array does not hold every civilisation's unique units. The union over all 32 civs gives 1,131 + id 0,
  and HP agrees with the pack on every shared id — the number to quote is **1,132**, and the earlier 962 was a probe
  measuring the wrong set.

## Not attacked, and named

- **The names are the game's words, normalised.** `docs/licensing.md` calls string tables a creative work and says they
  are never committed. What is committed here is a list of **identifiers** (`elite_cataphract`), derived with a
  mechanical normalisation, which is the thinnest form this could take — but it is derived, and the owner's plan (no
  reimport, gradual divergence) is what makes it defensible. Flagged once, here, rather than argued again.
- **Ids are still the key.** `names.toml` is `id -> name`; the tables still reference ids. Making names the reference
  (D97's direction) is the next step and is a bigger change: every effect command that names a unit (`[3, 38, 283]`)
  would need a name, plus the ~30 armour classes.
- **No civ dimension yet.** The dat's names are shared across civilisations here; a civ-specific name (`Briton` longbow)
  does not exist in this table.
- **The tool needs the importer's parser**, which is outside this repository (D4/D12). It says so when it cannot find
  it, and the committed table means a clone without the install still plays.

## Addendum: which unit gets the plain word (2026-11-02)

Suffix collisions by ascending id gave the plain name to the wrong unit: `Town Center` is both 71 (what an age turns the
centre into) and 109 (the one a match starts with), and by id alone **71** took `town_center` while the unit the engine
actually uses read `town_center_2`.

The rule is now **the unit that is nobody's upgrade result keeps the plain word**, read from the effect table's 227
kind-3 commands (a regex over the generated file, because this tool runs in the importer's environment and its
interpreter predates `tomllib`; it refuses to run if it finds fewer than 100 targets, so a change of file shape cannot
silently produce a wrong table).

Effect on the game's own vocabulary: the roles in `economy.toml` went from **11** disagreeing with `names.toml` to
**9**, and `town_centre` -> `town_center` is one of them. The nine that still differ are all a decision rather than a
defect:

| role | the unit | `names.toml` says |
|---|---|---|
| `archery_range` (87) | `archery_range_3` - three ranges share the word and 87 is one upgrade's result |
| `light_cavalry` (546) | `light_cavalry_2` - two unrelated units display "Light Cavalry"; 546 is a scout's upgrade |
| `boar` (48) | `wild_boar` | 
| `boar_carcass` (356) / `deer_carcass` (43) / `sheep_carcass` (595) | `wild_boar_corpse`, `deer_corpse`, `sheep_corpse` |
| `trebuchet` (331) | `trebuchet_packed` - the unpacked trebuchet is a different unit |
| `wall` (72) | `palisade_wall` |

Each is answerable in one line ("does the role name the unit, or the thing it represents?"), and they are the whole
remaining distance between the role vocabulary and the name vocabulary. Test: `the_base_unit_keeps_the_plain_word_and_
its_variant_is_suffixed` uses the 71/109 pair.

## Addendum: the five decisions, and where overrides live (2026-11-02)

The owner ruled on the five, and the rulings are data, not code:

| unit | name | why |
|---|---|---|
| 10, 14, 87 | `archery_range_1`, `_2`, `_3` | three records display "Archery Range"; none of them is "the" one, so all three are numbered |
| 546 / 37 | `light_cavalry` / `light_cavalry_2` | 546 is what a scout upgrades into, so it takes the plain word; 37 is the other record that shares it |
| 48 | `wild_boar` | the game's word; `boar` was my shorthand |
| 331 | `trebuchet_packed` | the record the game lets you train is the packed one |
| 72 | `palisade_wall` | the game distinguishes palisade from stone |

They live in `config/names_overrides.toml`, applied **after** the derivation, because the derivation cannot answer "which
of three identically named records is the one the engine means" - that is a judgement about intent, and intent belongs
in a file a human edits. The application is a swap: overridden ids give up their derived names first, then take the new
ones, so `546` can become `light_cavalry` while `37` becomes `light_cavalry_2`.

Overrides are validated like derived names: an unknown unit, a non-identifier, or a collision is reported and refused
(three tests). The project's table is checked for the four values that came from a decision rather than from the data.

**What is left, and it is mechanical:** three roles now name the wrong word - `boar` (should be `wild_boar`),
`trebuchet` (should be `trebuchet_packed`), `wall` (should be `palisade_wall`) - and `archery_range` now has three
numbered units, so the role must pick one (`archery_range_3` is the record the engine builds). Renaming a role touches
its references: 5 Rust files for `boar`, 3 for `wall`, none for `trebuchet`. That is the next commit, and it is a
rename, not a design question.
