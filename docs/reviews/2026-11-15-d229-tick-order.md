# Review: the tick's order is the original's

*Change: `crates/sim/src/world/step.rs` (+26 lines) and `crates/sim/tests/tick_order.rs` (new, three fixtures), plus the
documents the rule is recorded in (`docs/next-step.md`, `docs/decisions.md` D229, `docs/behaviour-diff.md` row 3,
`docs/mechanics/README.md` U18, `docs/mechanics/determinism.md`, `docs/dependency-tree.md`'s T12 row, and SPEC's
changelog row v1.175 plus its version header, which had been reading 1.159/2026-11-14 while the changelog was at v1.174 - a
stale claim in the file every session reads first). What changed in the engine: the ordered blow pass is
sorted by `(player, id)` instead of entity id, and a building at or below zero health when that pass ends takes no
production and no research that tick.*

## Performance

**+0.29%, inside the noise: HEAD 20.03 s median against 20.08 s over 24,000 acceptance ticks** (three interleaved pairs,
release build, nothing else running: A `19.70 / 20.03 / 20.32`, B `20.41 / 20.08 / 19.71`). The A side's own spread is
**3.1%**, so the sort's cost is below what this box can resolve - which is what the shape predicts: `work.strikes` holds
one entry per attacker **in reach this tick** (single digits in this scenario), the sort is `O(k log k)` and its key is one
binary search over the id-sorted entity list.

The change is deliberately not on the hot path in any other sense: `decide` is untouched apart from the sort at its end,
`turn_key` allocates nothing, and no per-entity work was added. The trainers' gate in `step_production` reads the owner
and the health in **one** `find` - the old code spent that same one lookup on the headroom check alone - so the pass is no
more expensive than before; the researchers' gate adds one `find` per researching building, only while something is being
researched.

**The acceptance match is unchanged**, and that is the more useful number: `hash=beb6c66f58e4045c` at 24,000 ticks and
`4640552242d6b45b` at 48,000, **both sides**, with `entities=154 repaths=277 made_room=0 repaths_body=68 repaths_ground=209`
at 24k and `148 / 552` at 48k. See "my own errors" below: I predicted it would move.

## Stability

*Gate: 192 test binaries, **877 passed, 0 failed, 20 ignored** (874 before this change, +3 fixtures), `fmt --check` 0,
`clippy --workspace --all-targets -D warnings` 0, 202 tool tests OK, `next-step --check` OK, `plan ok: 84 items, 120
citations`, `decisions --check` clean.*

- **The order contract is now the original's, with the mechanism read rather than inferred.** `FUN_00738720` (`0x738720`,
  `BaseWorld::update`) walks the players array at `+0x184..+0x188` from index 0 up - Gaia, then 1-8 - and inside a player's
  turn walks that player's object list object by object, skipping other owners' nodes. Each object gets one virtual call
  that **decides removal** (`+0xa0`; a 0 answer unlinks the node and calls vtable slot 0, the destructor) and otherwise one
  that **runs its update** (`+0x84`). The consequence the fixtures pin is the consequence of the *shape*: death is applied
  in the victim's own turn, so an earlier-ordered blow removes a man before any later object acts for him.
- **What is still simultaneous is named, not implied.** `decide` still reads the tick's opening state, so takes and
  deposits applied before the blow pass happen for a man who dies in it; movement deltas are in id order; and the gates are
  *stricter* than the original for a victim whose own slot came first (its turn would have run before the killer's). All
  three are in D229 and in `docs/next-step.md`, so the next slice starts from the truth rather than from "the tick is now
  the original's".
- **Every line is mutation-proved.** Removing the sort reddens `the_lower_player_acts_first_whatever_the_ids`; removing the
  trainers' gate reddens `a_building_destroyed_this_tick_finishes_nothing`; removing the researchers' gate reddens
  `a_building_destroyed_this_tick_finishes_no_research`. Each mutation reddens **only** its own test, so no gate is
  covering for another.
- **Determinism is untouched in kind.** The key is `(player, id)`, both of which are hashed state; the sort is total
  (`u8::MAX` for an id that is not in the world, so it sorts last) and `sort_by_key` is stable. Nothing new is carried
  between ticks, so the state hash gains no field.
- **A gate that a `Spawn` path could walk around was checked.** `start_next_jobs()` runs after both gates and can start the
  next job on a dead building; that is invisible (the entity is swept in the same tick, so the job is lost with it), so it
  was deliberately **not** guarded - a check no test could tell apart from nothing is not the rule (D223's lesson).

Known and accepted:

- **The gates are strictly-ordered rather than per-object.** A building killed by a *later*-ordered attacker would, in the
  original, have finished its job first; ours suppresses it. It is the price of the two-pass shape and it is written down.
- **`turn_key` relies on `entities` being sorted by id**, which `insert` maintains (it inserts before the first larger id).
  If that ever changes, the binary search silently returns "not found" and every strike sorts to the end - a wrong order
  rather than a crash. Named here because it is a coupling between two functions in different files.
- **The fixtures spawn player-2 buildings *before* `load_resources`**, because the start stock is applied once, to the
  players that exist at that moment. That is a real property of the engine (a player who joins later has no stock), not a
  fixture convenience, and it is commented in the file.

## My own errors, and what caught them

1. **Two fixture bugs, both mine, both found by the first run.** `next_id()` returned `max + 1` for two queued spawns, so
   both asked for id 129 and the second spawn was refused as a duplicate; and the training loop read `training` before the
   order had landed (commands land on the next `step`), so it panicked on "not training anything" instead of measuring. The
   ids are now explicit and the loop steps once first.
2. **I predicted the acceptance hash would move, and it does not.** The prediction is in the first draft of
   `docs/next-step.md` and was replaced with the measurement. The reason it does not: in that scenario every strike already
   lists the lower player first, so the sort is reached and is a no-op. An unchanged hash is *not* evidence that the sort is
   dead - the mutation is - but the prediction was a guess dressed as a gate.
3. **The research gate was written before its fixture**, so that half is proved by mutation rather than by a red run, and
   the two are not the same evidence. Recorded rather than glossed.
4. **The first A/B script produced no numbers** (`bc` is not installed) and its A side was a run of the *changed* tree in one
   round: the timings above come from the rewritten driver, which checks out HEAD for A and copies the change back for B,
   and restores the file in a `finally`.
