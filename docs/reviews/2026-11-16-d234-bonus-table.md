# D234 - the master list (R6): one table per player, five consumers reading it

**Scope.** `crates/sim/src/world/bonuses.rs` (new), `crates/sim/src/lib.rs` (the table field, `farm_food_bonus`,
`construction_rate`, `barred_by`, `civ_barred_unit`, `applies_to`, the `load_civs` hook), `crates/sim/src/world/research.rs`
(`modifiers_for`, the `apply_tech` hook), `crates/sim/src/world/report.rs` (`load_research` hook),
`crates/sim/tests/bonuses.rs` (three new fixtures).

**What it is.** Five consumers each decided which effects belong to a player over three effect tables. They now read one
table per player, built by one function that walks the three sources once and rebuilt on the two events that can change it.

## Performance

**Measured, three interleaved pairs, acceptance match, 24,000 ticks, one box, oracle = the same binary rebuilt from `HEAD`:**

| pair | HEAD | this change | delta |
|---|---|---|---|
| 1 | 21.69 s | 22.33 s | +3.0% |
| 2 | 21.73 s | 21.96 s | +1.1% |
| 3 | 21.71 s | 22.28 s | +2.6% |
| **median** | **21.71 s** | **22.28 s** | **+2.6%** |

Own spreads: HEAD 0.2%, this change 1.7%. The pair order was alternated (H,T then T,H then H,T) so drift in either direction
cannot be read as the effect. A first pair was discarded as warm-up: 25.19 s against 25.22 s, both sides dominated by page
cache.

**The design's premise was wrong, and it is written down as wrong.** `docs/civ-bonuses.md` argues the seam as a
correctness device, and this slice assumed it would also be faster (five walks replaced by one). It is **2.6% slower**. Why,
in order of size:

1. **The table clones every modifier, per player.** Each row carries its attribute as a `String`, so a lookup hashes a string
   and then walks rows scattered by allocation, where the old walk streamed the effect's own `Vec<Modifier>` in place - the
   thing caches are worst at.
2. **The rebuild allocates on each research completion**, where the old code allocated nothing.
3. **`farm_food_bonus` and `construction_rate` now walk every resource row of every source** and filter, where they walked
   three effect tables' commands. Same order of magnitude, different layout.

**The fix is named, not guessed, and not claimed until measured:** the **effect table is immutable for a match**, so
`attribute -> modifiers` belongs to the effect table and is built once for the whole pack; a player's table then holds
**effect ids per source** (a `[u32]` per source, no strings at all) and `modifiers_for` reads the shared index through five
ids. That removes both the clone and the string hash. It is a further slice, not this commit.

**What this does not cost.** Nothing per tick is added: `modifiers_for`'s 11 call sites keep their shape, and no new
allocation was introduced on the tick path (the `Vec` it returns existed before).

## Acceptance

`cb1f6a83a119a2a3` on **both** sides at 24,000 ticks (152 entities, `repaths=256`, 49 body / 207 ground) - the evidence that
this is a refactor and not a change of answer. Re-checked after the two fixes below, because the first two builds of this
slice did **not** match (`051e29ec69087825`).

## Stability

**Attack 1 - the table is stale at the moment a tech is applied.** This is the failure a cache invites, and it happened
twice in this slice, in two different places:

- The rebuild first sat at the **end** of `finish_research`. `apply_tech` computes every unit's new maximum health from
  `max_hp`, which asks for the player's hit-point modifiers - so during the apply the table still answered with the list from
  *before* the tech. Four fixtures caught it (`modifiers::loom_raises_every_villagers_health_immediately` read 25 where 40 was
  owed; `masonry_raises_building_health_by_a_tenth` 550 against 605; `wheelbarrow_...` 16000 against 17600;
  `a_speed_addition_...` 24000 against 31000). The rebuild now runs **immediately after** `researched` gains the tech and
  before anything reads a modifier.
- The rebuild in `load_civs` ran one line **before** the civ table was stored, so the table found no civ, cached no
  tech-tree rows, and the Spanish builder rate vanished
  (`build::a_spanish_builder_needs_385_ticks_where_a_british_one_needs_500`). It now runs after the store, with the reason
  written next to it.

Both are the same lesson and are recorded rather than smoothed over: a derived cache must be rebuilt **before** the next
reader, not after the writer.

**Attack 2 - the refactor changes an answer quietly.** The bars were folded from **every** source, so a kind-102 row sitting
in a team bonus started barring a tech that no consumer had ever barred. At 24,000 ticks the match had the **same entity
count (152) and the same repath counts (256/49/207)**, so no fixture and no count moved; only the acceptance hash did
(`051e29ec69087825` against `cb1f6a83a119a2a3`). The bars now come from the tech tree only - the source `barred_by` has
always read - and the underlying question (what a bar inside a team bonus *should* do) stays open in `docs/civ-bonuses.md`
rather than being answered by a refactor.

**Attack 3 - the second research is lost.** The classic once-only fill: `if researched.len() == 1 { rebuild }` was applied as
a mutation and reddened both farm fixtures (`every_farm_tech_reaches_the_plot_and_the_second_one_counts_too` read 175 where
250 was owed at the *first* grant, and `a_team_bonus_and_a_research_are_one_answer` 220 where 295 was owed). Restored, both
green.

**Attack 4 - the sources get merged.** `modifiers_for` never reads the civ's tech tree, `farm_food_bonus` never reads it, and
`construction_rate` reads it **first**. The table keeps the source on every row instead of merging them, and each consumer
filters what it folds; the acceptance hash is the check that no consumer started reading a source it did not read before.

**Attack 5 - derived state leaks into the hash or the save.** `bonus_tables` is not hashed and not saved, following
`bonus_effects`' rule; the hash stayed `cb1f6a83a119a2a3` through the change, which is the evidence that the table is derived
and not state.

**Not attacked, and why.** The table is rebuilt on two events only. Two more could in principle change it and neither exists
today: a **civ being changed mid-match** (there is no such command - `load_civs` runs once) and a **team bonus being added**
(it is set in the same loop that sets the civ). A third is a real gap: **saved-game restore**. There is no `from_state` in the
tree yet (grepped: none), so a restore path does not exist to test; when P1 builds one it must either go through `load_civs`
or call `rebuild_bonuses` per player, and this note is the reminder.
