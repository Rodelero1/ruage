# The AI leaves the scenario file: `config/ai/base.toml` (2026-11-01)

Scope: `config/ai/base.toml` (new - the 14 rules that were inside `config/acceptance.toml`), `config/acceptance.toml`
(now names a personality and holds nothing else but its duration), `crates/sim/src/script.rs` (`Scenario.ai`,
`Personality`, the loader), `crates/sim/src/lib.rs` (exports), `crates/data/src/pack.rs` (`ai/base.toml` joins
`PACK_FILES`, 9 -> 10), plus four tests in `crates/sim/tests/scenario.rs`.

**Why the move.** D94, in the owner's words: *"whatever sets how the AI player behaviour ... has to go to separate folder
for AI."* A scenario is a match; a personality is behaviour. Keeping the 14 rules inside `acceptance.toml` meant the
behaviour of the AI was a property of one test fixture, unreachable from any other match.

## What changed, and what did not

- `config/ai/base.toml` holds the 14 rules, unchanged in content, with the reasoning that used to sit in the scenario's
  header now attached to the rules it explains. `schema = 1` is its own version: it is behaviour, not world data.
- `config/acceptance.toml` keeps `schema`, `duration_seconds` and gains `ai = "base"`. It has **no** `[[rule]]` blocks.
- `Scenario` gains `ai: Option<String>`, resolved as `ai/<name>.toml` beside the scenario file.
- `load_scenario_file` merges the personality's rules into the scenario's; `load_scenario_str` refuses a scenario that
  names one, because text has no directory to resolve against.
- The personality joins the pack identity, so two peers whose AI differs are refused rather than playing two games.

**No engine behaviour changed**: the same 14 rules, evaluated by the same runner. What moved is where they are read from.

## Performance

| what | number |
|---|---|
| `cargo test -p ruage-sim --test scenario` (22 tests, one of them a full-minute run of the acceptance match) | **61.98 s** |
| the new loader test | **0.00 s** |
| pack load | one more 6 KB file, in a load that already reads nine |

The loader adds one `read_to_string` and one `toml::from_str` per scenario load - the acceptance run loads the scenario
once per test. Nothing is added to the tick.

## Stability

- **A missing personality is refused by name**: the message names the personality *and* the file it could not read, so
  the author does not have to guess which of the two is wrong.
- **Two sources for one AI is refused**: a scenario with `[[rule]]` blocks *and* `ai =` fails, with the reason ("the
  behaviour belongs in one place"). Without it, the merge would silently prefer one and ignore the other.
- **A scenario held as text cannot silently play with no AI**: `load_scenario_str` refuses `ai =`, naming the loader that
  can resolve it.
- **The rules are byte-identical to the ones that were in the scenario file**, so the acceptance match's behaviour is
  unchanged by construction; the test that says the opening runs without refusal passed before and after.

### Mutation testing (the discipline the owner asked for)

| mutation | result |
|---|---|
| the personality's rules are never merged into the scenario | **FAILED** - `a_scenario_takes_its_rules_from_its_personality` |
| the "rules *and* a personality" guard removed | **FAILED** - `a_scenario_with_rules_and_a_personality_is_refused` |
| the "text cannot name a personality" guard removed | **FAILED** - `a_scenario_held_as_text_cannot_name_a_personality` |

All three guards are pinned by a test that dies when the guard goes.

### My own errors in this slice

- **Written code-first again.** The Rust change came before the tests, which is the second time today (the pack-hash
  slice was the first). The mutation runs above are what stands in for the RED; the rule was not followed, and saying so
  is the least that is owed.
- **Three test fixtures were missing `duration_seconds`,** a required field, so the refusals they asserted never
  happened: `TOML parse error ... missing field 'duration_seconds'`. The tests failed for a fixture reason, not a
  behaviour reason - which is exactly the kind of "passing for the wrong reason" that a run catches and a reading does
  not.

## Not attacked, and named

- **`[policy]` is still in `economy.toml`.** D94 puts villager distribution in the AI folder, and it is the next slice:
  the share table has to move into the personality, which means `Economy` loses the field and the five call sites of
  `apply_content_policy` change. Deliberately not mixed into this commit - it is a different change with its own risk.
- **One personality, and `PACK_FILES` is a fixed list.** A folder of personalities cannot be hashed by that mechanism
  without a *sorted* directory walk, which is a design task (order-determinism, what happens to an unlisted file) rather
  than a line of code. Until then, each personality is named in `PACK_FILES` by hand.
- **`Personality` denies unknown fields**, so the file cannot yet carry `[policy]` or `[tuning]`. That is deliberate
  while it holds only rules: a silent extra table is a typo nobody sees. The field arrives with the slice that reads it.
- **No per-civ delta yet** (D95). `config/ai/civ/` does not exist; the loader has no notion of a civ overlay.
