# D88: blows land in order, and the determinism lint is enforced

*2026-11-01. Adversarial review of the owner's U18 decision ("units cannot trade killing blows, follow original") plus the
first of the adoptables (`clippy::iter_over_hash_type`).*

## What changed

- **Melee blows are applied in order and a unit that died earlier in the same pass does not swing** (`crates/sim`, the
  `strikes` loop). The pass keeps a small `killed` list; a blow whose attacker or target is on it is skipped. Everything
  dead before the pass was swept at the end of the previous tick, so that list is the whole of "already gone".
- **`[workspace.lints]` denies `clippy::iter_over_hash_type`** in all four crates. Determinism rule 3 ("stable iteration
  order — by entity id, never hash order") now has a gate instead of a review habit.

## Performance

**Measured, and the honest reading is "no change outside combat".** The idle probe (no combat at all) best-of-3:

```
126 entities   3.19 us/tick   25.3 ns/entity/tick      1126 entities  26.28 us/tick  23.3 ns/entity
376 entities   8.91 us/tick   23.7 ns/entity/tick      2126 entities  50.63 us/tick  23.8 ns/entity
626 entities  15.04 us/tick   24.0 ns/entity/tick
```

against 27.2 / 26.0 / 27.1 / 26.5 / 32.3 recorded earlier in the session — the difference is this shared box, not the
change: nothing in the idle path reads the new list.

**The guard's shape is the performance decision.** A blow's liveness is checked with `Vec::contains` on a list that is
empty unless something died this tick, so the common case is two comparisons and no allocation. The obvious alternative —
`self.find(attacker).is_none_or(|e| e.hp <= 0)` — is a linear scan of the world per blow: a hundred simultaneous blows on a
3,000-entity map would pay **600,000 comparisons a tick** for a fact the pass already knows. It was written that way first
and replaced before committing.

**Acceptance match: same hash `91e869fcc92d606c`, `players=1`** (48,000 ticks, 24.3 s wall on a loaded box). Same hash
means the rule never fired in that run — no two villagers traded killing blows on that map — which is the
path-equivalence signal: the change is real but not triggered there.

## Stability — what was attacked

1. **Blast victims can be attackers later in the same pass.** My first version recorded only the aimed target's death, so a
   mangonel's splash could kill a unit that then still swung. The blast branch now records every victim whose health fell
   to zero, and `killed` is consulted for both the attacker and the target of each blow.
2. **A blow aimed at something already dead is skipped**, so no damage is credited to a corpse and no retaliation is
   triggered from one. `blows` still records (victim, attacker) for the two rules that read it — the animal's meat and
   retaliation — so kill attribution is unchanged for everything that did land.
3. **Projectiles are deliberately outside this rule.** An arrow is an entity with its own lifetime: it lands when it
   lands, even if its shooter died while it was in the air. The asymmetry is intentional and written down here rather than
   discovered later as a "bug".
4. **The lint is enforced, not declared.** Verified by writing a throwaway test that iterates a `HashMap` and watching
   `cargo clippy … -D warnings` fail with *"iteration over unordered hash-based type"*; the probe was then deleted. A lint
   nobody has seen fire is a claim, and this project does not ship claims.
5. **The new file does not disturb the old tests:** `combat`, `retaliation`, `skirmish` and `blow_order` all pass, and the
   acceptance match still wins.

## What this does NOT settle

- **Whether the original applies blows by object id, by some other order, or per-side.** We apply them in the order the
  decide pass collected them, which is entity-id order because that pass walks the entity list. That is *a* deterministic
  order and it satisfies "cannot trade killing blows", but it is not yet the original's order — register row 3
  (`docs/behaviour-diff.md`) stays `needs-oracle` until the recording or the binary says which.
- **Ranged simultaneity.** Two archers whose arrows land on the same tick still both hit: the rule as implemented covers
  melee swings and instant shots, not arrows in flight. If the owner wants arrows ordered too, that is a second decision.
