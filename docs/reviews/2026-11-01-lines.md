# Lines: the AI's unit families, checked against the pack (2026-11-01)

Scope: `config/lines.toml` (new), 12 roles added to `config/economy.toml`'s `[role]` table, `tools/lines.py` (new) and
`tools/test_lines.py` (new, 12 tests). No Rust changes: nothing in the engine reads a line yet.

**Why a line at all.** D95: the AI names a *family* ("the knight line"), and the resolver takes the last member the civ
can actually field, so the tech tree - not a scoring function - decides what Saracens field. That was the owner's answer
to "train the best cavalry I can field" being ambiguous: the civ file says what answers a line, and the pack says how far
the line goes.

## What the pack actually says

Derived from the effect table's `kind = 3` commands (227 upgrade edges), then authored into `config/lines.toml` and
re-checked against those edges:

| line | members (unit ids) | evidence |
|---|---|---|
| `knight` | 38 -> 283 -> 569 | hp 100/120/160, attack 10/12/14 |
| `spear` | 93 -> 358 -> 359 | the existing roles, and the +15/+22/+32 bonus against the cavalry class |
| `skirmisher` | 7 -> 6 -> 1155 | hp 30/35/35, +3 against the archer class |
| `scout` | 448 -> 546 -> 441 | hp 45/60/75, attack 3/7/7 |
| `militia` | 74 -> 75 -> 77 -> 473 -> 567 | hp 40/45/60/60/70 |

The dat's *names* are shifted (283 is the cavalier and says `PALDN`; 569 is the paladin and says `HEROC`; 7 is the
skirmisher and says `XBOWM`), which is why the roles are written from ids and the ids are checked by derivation rather
than trusted from a name.

## Performance

`python3 -m unittest tools.test_lines` - **12 tests in 0.33 s**, which includes parsing `effects.toml` (a 227-edge table)
twice. `verify()` is one pass over the lines plus one dictionary lookup per consecutive pair; `derived()` is a DFS per
root over the same edges. Neither is on any hot path - this is an authoring tool, run by hand and by the test suite, never
per tick.

## Stability

- **The table cannot silently drift from the pack.** Every consecutive pair is checked against the effect table, and the
  test fails with the line, both roles and the missing upgrade named. This is the D91 shape: authored where a human must
  decide, derived where the data already knows.
- **`Non-Research` effects are excluded.** They swap a unit for free (an age-up or a scenario grant) and are not a tier
  anyone can buy; counting them would let a line claim a tier no civ can field. Named in the code, not just in this note.
- **A branch resolves deterministically**: `chain_from` takes the longest path and breaks ties on the lower id, so the
  answer never depends on table order.
- **An unknown role is refused by name**, not by index, because a role typo is the most likely error and `-1` in a
  message would be useless.

### My own errors in this slice

- **A test asserted a message I had written badly.** `test_a_line_in_the_wrong_order_is_refused` expected the word
  "paladin" in a message that named only the unit *after* the break. The test was right about what a reader needs, so
  the message changed to name both sides (`puts 'cavalier' after 'paladin'`), and the test now asserts both. Changing
  production code to satisfy a test is only defensible when the expectation is better than the code, and here it was -
  but it is worth naming, because the easy version of this mistake is fitting the code to a wrong assertion.
- **The first run was RED for the right reason** (`ModuleNotFoundError: No module named 'lines'`), which is the state a
  test should be written in; the ordering was honest this time, unlike the pack-hash slice earlier today.

## Not attacked, and named

- **No engine consumer.** `config/lines.toml` is not in `PACK_FILES` and nothing in `crates/` reads it, deliberately: the
  same argument used against hashing `movement.toml` - a file in the identity that nobody consumes looks like protection
  without being any. It joins `PACK_FILES` in the commit where the AI slice resolves a line, together with the code that
  uses it.
- **Civ availability is not modelled.** A line says what the family *is*; which tiers a civ can research is the tech
  tree's job and is not represented yet, so "the last member I can field" cannot be resolved today. That is the next
  slice's work, not this one's.
- **Branches are collapsed.** The pack has units that upgrade two ways (one per civ); the derivation takes the longest,
  which is right for a family and wrong for a specific civ's tech tree. When civ availability lands, a line may need to
  be a *set* of paths rather than one path - flagged here so it is not discovered as a surprise.

## Addendum: the owner asked whether this was really reviewed, and it was not (2026-11-01)

The first version of this review found one defect (a badly worded message) and called it done. The owner asked the
direct question, and the answer was no - a review that finds nothing in a fresh tool is a review that did not try. So
the change was attacked properly, by mutation and by probing the API, and **three defects came out**:

1. **A role naming a unit the pack does not carry was accepted.** `verify` only compared upgrade pairs, so a *one-tier*
   line - legal, and a real case for a civ whose family has one member - skipped every check. `verify` now takes the
   pack's unit ids and refuses `role 'ghost' -> unit 99999`, which the pack does not carry.
2. **A missing `config/lines.toml` died with a raw `FileNotFoundError` traceback.** It now returns 2 with a sentence
   ("it is content, not generated, so it has to be authored"), the same contract the other tools keep.
3. **The determinism claim was unpinned.** Reversing the branch traversal changed nothing visible, because the
   `sorted()` call normalises the order - so that mutant is not a defect, it is a redundant safeguard. Removing the
   *lower-ending-id tie-break* was the real one, and it survived the whole suite. A fixture was needed whose two
   equal-length paths end at 9 and 4 rather than at 2 and 3: the first version of the test used the latter and could not
   tell the tie-break from the traversal order. With the path endings separated, deleting the tie-break fails.

### The mutation table, as run

| mutation | result | reading |
|---|---|---|
| remove the `Non-Research` filter | **2 failures** | caught |
| accept unordered membership instead of ordered pairs | **2 failures** | caught |
| remove the unit-existence check | **1 failure** | caught (after defect 1 was fixed) |
| remove the missing-table guard | **1 error** | caught (after defect 2 was fixed) |
| remove the lower-ending-id tie-break | **1 failure** | caught, but only after the fixture was strengthened |
| reverse the branch traversal order | **passes** | *not* a defect: `sorted()` makes input order irrelevant, so the tie-break is the only ordering rule that can bite |

Tests went 12 -> 16, and the four new ones each exist because a mutation or a probe got through without them.

**What this addendum says about the process:** the first review was written from what the code was *supposed* to do. The
second was written from what it *did* when pushed. The difference was three defects, one of them a hole in the verifier
that a single-tier line walked straight through.
