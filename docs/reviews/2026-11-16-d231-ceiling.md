# Review: the population ceiling is read at the spawn

*Change: `crates/sim/src/world/step.rs` (five lines in `step_production`'s trainers loop) and
`crates/sim/tests/population.rs` (one new fixture). What it does: the `capped` flag for a player is recomputed when a job
completes, so a building that finishes second in the same tick sees the population the first one just spent.*

## Performance

**+0.0% on the acceptance match, and the sign of the difference is noise: 24.13 s before the change against 21.95 s after
it, 24,000 ticks, one release run each.** The after-run being *faster* by 9% is the box, not the change - the same
command has moved by up to 3% between adjacent runs today - so the honest reading is that the cost is below what this
machine resolves. The call count goes **down**: the recompute is `population()` + `population_cap()` - both linear scans -
and it now runs **once per unit trained** rather than once per building per tick, which is a strict reduction in how often
either is called whenever a player has more than one trainer. Only ticks on which a job *completes* pay anything at all,
and those are the ticks that place a unit.

**The acceptance match is bit-identical**, so the change is not even reached by that scenario: `cb1f6a83a119a2a3`, 152
entities, 256 repaths, `repaths_body=49`, on both sides of a release A/B (24,000 ticks). That is the useful half of the
measurement: a rule that fires only on a collision the match never has cannot be found by the hash, so the fixture is the
evidence - and the fixture's own red run **is** the mutation (population 6 against a cap of 5).

## Stability

*Gate: 193 test binaries, **880 passed, 0 failed, 20 ignored** (879 before this change, +1 fixture), `fmt --check` 0,
`clippy --workspace --all-targets -D warnings` 0, 202 tool tests OK, `next-step --check` OK (11,198 bytes after the
compaction), `plan ok: 84 items, 120 citations`, `decisions --check` clean.*

- **The defect was real and the red run says so**: two barracks, one slot, **population 6 against a cap of 5** - the second
  soldier arrived out of a ceiling that was already spent. The failure is the fixture's own first assertion, so the fixture
  is not measuring a shape it cannot tell apart from nothing.
- **The second job is held, not lost.** The fix does not drop the job: the trainers loop `continue`s before the countdown,
  which is D34's pause, and the fixture asserts that the losing barracks still carries its `training` job afterwards. A fix
  that satisfied "one arrived" by discarding the other would fail that assertion.
- **The pause is visible to the panel**, in the sense that `training_pauses` is untouched by this change: the capped path
  has always been the plain `continue`, not the `NoRoom` pause, and this change keeps it that way.
- **`capped` cannot go stale in the other direction.** Population only rises during this phase (a spawn), and a spawn is the
  only thing that can make a player *newly* capped; a unit dying happens in the sweep, after this phase, so the flag is
  always refreshed at least as often as the fact it holds can change.
- **A missing player index cannot panic**: the slot is clamped with `.min(MAX_PLAYERS - 1)` exactly as the read is, so a
  player id outside 1..=8 lands on the same slot for both.

Known and accepted:

- **This is one case of the inner loop, not the inner loop.** T12 stage 3 - deciding and applying one object at a time - is
  still not built, and `docs/next-step.md` prices it with the enumeration that found this case: every remaining member of
  that class is a **one-tick latency** on a quantity already clamped at apply time.
- **A stranger could read `capped` as a per-tick fact.** It is not: it is the answer as of the last spawn in this phase.
  The comment says so at the site; a future pass that reads it before this loop would get the tick's opening answer, which
  is the bug being fixed.

## My own errors

1. **The first fixture read `training` before the orders landed** - commands are queued, so both barracks read `None` and
   the test failed on its own premise rather than on the rule. It steps once after the orders now.
2. **The fixture's population arithmetic was checked against the wrong start** - the seeded opening is three villagers
   **and a scout** (population 4), not three, so "one free slot" had to be asserted rather than assumed; the test asserts
   `cap - population == 1` before it does anything, so a fixture that drifts cannot silently measure nothing.
