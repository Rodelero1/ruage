# D209 - the smaller pencil: routes bend round a body inside a tile

**Built, working in isolation, and parked with the triage below.** The mechanism the last three slices were missing; the
remaining failures are three obsolete tests, three gather regressions I have not explained, and the rest of the same class.

## What it is

`short_range_clear(walk, scale, from, to, radius, avoid_tiles, bodies)` - the same search as `short_range`, with two
changes:

- **bodies are discs, not tiles**: `bodies` is `(centre, clearance)` and the route keeps `clearance` clear of each centre,
  tested exactly in integers (`cross^2 >= clearance^2 * length^2` - no division, no sqrt, i128);
- **eight shoulder points** per body at the clearance, so a route can bend to the left or right of a man *inside* one tile,
  which a tile-corner graph cannot express.

The clearance is `my radius + his` - the distance the original grows its obstacle rectangles by - and **exactly that, with no
margin** (see the error below). A route may always *leave* a disc it already stands inside, or a man who has just met
somebody would have no legal first step.

`stander_bodies` feeds it: every unit that did **not** move on the last tick, excluding the start and goal tiles. That is the
original's rule for its per-search rectangles (`FUN_007f9d80`: insert iff not ignored and velocity is zero), and the tile set
is kept alongside it for the fallback search that can only think in tiles.

## Performance

Not measured this round, and that is a gap: the D208 half measured 2.3x slower and D209 changes the search again, so the

## Stability

- **Exact integers only**, no float and no sqrt; `clears_disc` is a pure predicate and `contains_disc` is the only licence to
  move *out* of a disc.
- **Deterministic:** bodies come from state (positions and `last_moved`), the disc and node order is fixed by iteration order,
  and the shoulder points are computed, never drawn.
- **Two of my own errors, both found by measurement:** the first `stander_bodies` filter skipped **every body in a fresh
  world** (`last_moved + 1 >= tick` is true at tick 1 when the sentinel `0` means "never moved"), so plans kept answering
  with a straight line through a man standing there since the seed; and a one-eighth-tile clearance margin, added to stop the
  mover cutting the circle, put every neighbour's place inside a standing worker's disc and broke the gather ring (18 tests).
  Both are fixed - the margin is gone, "never moved" is standing.

## Second follow-up: the place route, and the one guard still red

**A place route is not a walk.** `radius == 0` is how a gatherer is sent to his reserved place, and the ring already
reserved that place against every other body (D186/D188). Modelling the crowd as obstacles *again* there made a dense little
map unroutable - `NoPath from (0,0) to (3,1)`, which is exactly the tree that sat at `Fixed(100000)` untouched. A place route
now ignores standers and the reservation does the work: `gather` **21/21**.

**A step out of a body must widen the gap.** The visibility test allowed *any* edge from a node inside a body's clearance
circle, and a straight line from inside it through it is such an edge - the walker simply aimed at his goal through the man.
Only a step that ends farther from that centre than it began is now a step out.

**One guard is still red, and I am not pretending otherwise.** `group_overlap::a_mate_who_is_stopped_becomes_solid` still
measures **closest 4207 raw against an 8000 reach** after the stop. Since the search now refuses to enter or cross the disc,
the remaining explanation is that **the re-plan is not happening at all** for that walker after the stop - the measurement is
identical to before the two rules above, which a route-level fix would have moved. That is where the next pass starts, and it
is one `trace_steps()` away from being established.

## The original answers the last guard directly: it re-seeds the start

`FUN_007fb220` (the low-level search), verbatim:

```c
local_16 = FUN_007fb8e0();          /* is the START point inside an obstruction? */
if (local_16 != '\0') {
    FUN_007fb1d0(1, iVar2);
    pfVar7 = (float *)&DAT_009e252c;        /* a fixed table of directions */
    local_30 = param_5 * 2.0;               /* **twice the radius** */
    local_15 = '\0';
    do {
        local_38 = pfVar7[-1] * local_30 + *param_2;    /* start + 2r * direction */
        local_34 = *pfVar7  * local_30 + param_2[1];
        cVar1 = FUN_007fb8e0();                         /* is that point free? */
        if (cVar1 == '\0') {
            FUN_007f97c0(1, 1, iVar2, &local_38, local_c, ...);   /* re-seed the search there */
            local_15 = '\x01';
        }
        pfVar7 = pfVar7 + 2;
    } while ((int)pfVar7 < 0x9e25ac);
    if (local_15 == '\0') return 3;         /* every offset blocked: no low-level path */
}
```

So the game does exactly what the stopped-mate guard needs - **when the search starts inside a body, it offsets
the start by `2 x radius` along each direction of a fixed table, re-seeds from the first free one, and only gives up
(`return 3`) when all of them are blocked.** The table (`DAT_009e252c`, 0x80 bytes of float pairs) holds unit-ish
directions: `(1,1)`, `(0,0)`, `(-1,-1)`, `(0,0.707)`, `(0.707,0.707)`, `(-0.707,-0.707)`, ... - a sampled ring, not four axes.

Our D210 rule is therefore not "back off, then go round" as a design of ours: it is **this**, with the same `2 x radius`
distance and a fixed candidate ring.
