# Review: the damage register's row 2, read directly

*Change: documentation only - `docs/behaviour-diff.md`'s damage row moves from "candidate located, not ruled" to "same arithmetic, floor unproven", and D227
records why. The two functions were decompiled rather than summarised. **No simulation code changed.***

## Performance

**Zero**: no code path is touched (`git diff --stat` on `crates/` is empty), so the gate's numbers are unchanged - 191 binaries, 874 passed, 0 failed, 20 ignored.
What the slice costs is the reading time (two decompilations, ~30 s of tool time once the target was open) and it buys the removal of a **misleading debt**: the
row invited a rewrite of `damage_between` into a per-entry drop, which measures as a no-op because dropping a non-positive term and clamping it at zero are the
same arithmetic.

## Stability

- **The claim is narrower than the one it replaces, and narrower than "same".** Five facts are now read rather than inferred (three slots at named offsets, the
  multiplier at `[ebp+0x28]` with truncation, the float armour table at `this+0x3c` indexed by class, the fold into class 3, the per-slot `-1` drop), and the
  accessor is confirmed to be `1.0 x (slot1 + slot2 + slot3)` with **no clamp**.
- **The one open number is named with the reason it is open.** `sub_745060`'s address is taken five times with zero direct callers, so it is a **virtual method**
  and the 1-damage floor sits behind an indirect call. That is a different next step from "read another function", and the row now says so.
- **Two real differences are recorded rather than smoothed over**: per-class **attribution** (the original folds leftovers into class 3, we do not - harmless
  while only the sum is read) and **armour type** (float there, integer here - latent, because no shipped modifier is fractional).
- **The decompiler's own limitations are respected.** The pseudo-C is register-level with 7 unstructured jumps and 27 `__asm` instructions in this function, so
  the *offsets and the shape* are what is claimed; a per-register reading of which value is stored where is not, and D227 does not claim it.

Known and accepted:

- **Row 2 is not "ruled"** and the register still reads 1 of 12. Ruling it needs either the vtable's users or a recorded game where a fully-armoured attack lands
  for 0 rather than 1 - the floor is the only thing left, and it is one number.
- **The evidence is a clean-room decompiler's output**, not a debugger trace, and this review says so rather than implying more.
