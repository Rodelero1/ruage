# Translation: what it would take, and what it must not touch (2026-11-02, owner's request)

Owner's question: *"Would it be also possible to make the game translatable via gettext tools?"* Answer: yes, and this
file records the shape so a future session does not have to rediscover it. **Nothing is implemented.**

## There is almost nothing to translate yet, and that is the first fact

- **The only text drawn is digits.** `crates/view/src/font.rs` is a bundled 3x5 bitmap font of ten digits and a slash
  (D82) - stock, population, tick. No word appears on screen, so no player-visible string exists to translate.
- **Every other sentence is a developer diagnostic.** About **136** `format!`/`write!` sites across `crates/sim` and
  `crates/data` - `"unit {id} is not in the unit table; the config points at an id the data lacks"` and its relatives.

So a font that can draw letters is the prerequisite for translating anything a player reads, and that is a larger
decision than gettext (parser, licence, hinting) which D57/D82 deliberately avoided.

## Three kinds of text, three different answers

| kind | examples | translatable? |
|---|---|---|
| **Identifiers** | `elite_cataphract`, `palisade_wall`, `town_center` | **No.** An identifier that changes with the locale is not an identifier (D97). |
| **Display text** | a unit's name in a tooltip, "Cancel", "Age: Feudal" | Yes - and it is the only kind that needs a font first. |
| **Diagnostics** | refusals, `SimError`, `ConfigError` | Yes, and see below - but the refactor is worth doing for testing alone. |

## What gettext would need

1. **Keys, not prose.** `xgettext` cannot see through `format!("...{id}...")`; the usual keyword tricks still leave a
   sentence concatenated in Rust. The robust shape is a `Message` value - a key plus arguments (`Message::MissingUnit
   { id }`) - rendered by a catalogue at the edge. That refactor pays off *before* translation exists, because tests can
   then assert **which** message fired instead of matching English substrings (several do today).
2. **A catalogue.** `.po` files per locale, compiled to `.mo`, looked up through `gettext-rs` (libintl) or a small
   pure-Rust reader. `cargo-i18n` can extract `t!()`-style macros; a `Message` enum can be extracted mechanically by a
   one-off script instead, which is less clever and easier to check.
3. **A locale switch that is not in the simulation.** `LANG`/`LC_MESSAGES`, or an explicit `[ui] locale` in content.

## The rule that must not be broken

**A translated string must never enter simulation state, the state hash, or the pack identity.** Two players with
different locales run the same match; if a locale could change a hashed value they would desync on nothing. Today every
message is formatted at `Display`/HUD time, which is already the right side of the line - a future change must not move
formatting into the tick.

## Order of work, when someone wants it

1. **Message keys** for the diagnostics (testable immediately, translatable later).
2. **A font with letters** - the gate for anything player-visible.
3. **Display text** in content, per locale, keyed by identifier.
4. **gettext as the adapter**, if `.po` tooling is still wanted once 1-3 exist. Nothing in the design needs it earlier.
